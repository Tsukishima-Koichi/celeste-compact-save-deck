# Compact Save Deck：规划与环境调研

调研日期：2026-11-24。范围：开发环境、技术可行性、第一版产品规划；尚未实现或部署 Mod，也未修改游戏配置或存档。

## 1. 结论

可实现为独立的 **C# / Everest Core 代码 Mod**。使用 Celeste 自身的 Monocle / FNA 界面绘制与输入系统，在原始竖排存档菜单上加入 **可展开的堆叠卡组**。按照用户最新要求，未归组存档卡片保持原样，已归组存档收拢成卡片堆，展开后组内存档仍然竖排；选择存档后的地图选择与游戏界面沿用正常流程。

布局要求已于 2026-11-24 更新：取消此前的网格、固定每屏 12 卡和卡组侧栏方案。空间节省来自折叠卡组，而非缩小原版存档卡片。

同日补充要求：未归组存档在外层竖排列表中的位置，以及卡组内存档的竖排顺序，均可手动调整并持久保存，纳入首版。

本机开发基础基本齐全。官方当前 Core 模板、实际 Celeste 程序集和运行配置均指向 **.NET 8**。推荐目标框架 `net8.0`，使用现有 .NET SDK 10.0.201 和 Visual Studio 2026；SDK 版本不需要与目标框架版本相同。首次正式搭建仍需验证 NuGet 还原、编译、部署和游戏内加载，不能把“工具已存在”当成完整链路已经测试通过。

主要技术难点不是卡片绘制，而是：大量存档下的加载与切换成本、正确复用 Everest 的存档操作、与其他修改存档菜单的 Mod 协作。

## 4. 产品定义与第一版范围

**一个卡片对应一个完整的 Celeste 存档槽；一个卡组对应用户定义的用途分类。**

例如：主线、草莓酱练习、金草莓挑战、速通、测试、归档。这些只是可选的初始名称，用户可以自由创建和改名。一个存档可能同时包含官图和多个地图包的进度，因此“当前地图包”只能作为提示，不能可靠地代表存档类型。

第一版采用一个存档最多归属一个卡组。未归组存档直接出现在原始竖排列表中，不强制装入“未分类”卡组。卡组和未归组存档共同构成同一条纵向列表；归组后，该存档只在其所属卡组展开时出现，不在外层重复展示。多标签、聚合视图与自动分类放到后续版本。

### 布局与信息

- **整体竖排**：保留原存档菜单的背景、纵向浏览方式和原卡片尺度。未归组卡片的造型、信息、选中反馈及普通操作保持原有表现。
- **折叠卡组**：在原列表中约占一张存档卡片的空间；正面采用与原卡片协调的材质和轮廓，展示卡组名、存档数量与展开提示。后方露出 2–3 层轻微向右下错开的卡片边缘，以细阴影表现叠放；层数设上限，存档数量以数字显示。此为首版暂定样式，后续根据用户查看反馈调整。
- **展开卡组**：在原位置展开，组标题收成较矮的可折叠标题行，组内存档向下依次竖排，后续列表项顺势下移。组内仍使用正常存档卡片，宽度与外部卡片一致；可用侧边细线标识归属，不因缩进而压缩卡片。
- **收起卡组**：组内卡片向组标题位置收拢，恢复卡片堆；焦点回到该卡组，避免列表突然跳到顶部。
- **信息继承**：单个存档继续展示原版/Everest 的存档信息；卡组封面不把多份存档的进度合并成容易误解的百分比。
- 名称太长时截断，聚焦时显示完整组名；空卡组、未加载数据、损坏存档分别给出清晰状态。
- “新建存档”沿用原有入口与行为；新增归组选择不改变新存档进入游戏的流程。
- 简体中文和英文使用 Dialog 本地化；避免硬编码字符串，验证中文输入与缺字情况。

布局关系示意（只说明纵向顺序，不代表最终美术）：

```text
折叠时                         展开“练习”后
原版存档卡 A（未归组）          原版存档卡 A（未归组）
▸ 练习 · 3 个存档 [卡片堆]      ▾ 练习 · 3 个存档
原版存档卡 B（未归组）              原版存档卡 C
▸ 挑战 · 2 个存档 [卡片堆]          原版存档卡 D
                                   原版存档卡 E
                               原版存档卡 B（未归组）
                               ▸ 挑战 · 2 个存档 [卡片堆]
```

示意中的缩进仅表示归属，实际卡片对齐与宽度保持一致。首版暂定允许多个卡组独立展开，新卡组默认收起，返回存档菜单时恢复之前的展开和焦点状态。

### 操作

- 键盘/手柄上下来回浏览同一条纵向列表；聚焦折叠卡组时，确认展开并定位到组内上次选中的存档，首次展开默认选中第一个。空卡组展开后保留标题焦点并显示空状态。
- 聚焦已展开卡组标题时，确认收起；聚焦组内存档时，确认执行与普通存档相同的选择操作。组内存档的菜单关闭后，取消可返回并收起所属卡组，再次取消沿用原菜单的返回行为。
- 肩键或可重绑快捷键可作为跳到相邻卡组标题的补充，翻页键浏览长列表；具体键位以不冲突于原存档操作为前提。
- **大量卡组支持直接跳转**：使用按需打开的卡组查找/选择浮层，跳转仍落回原竖排列表中的对应卡组，不增加常驻侧栏。
- 记录列表的视觉锚点、展开状态和各组上次选中的存档；展开/收起时尽量保持当前操作位置稳定。存档移走或删除后将焦点落到合理的相邻项。
- 鼠标点击与滚轮作为补充，所有核心操作均可只用键盘或手柄完成。
- 通过管理操作选择需要归组的存档并创建卡组，或加入已有卡组；支持移出卡组及卡组改名、排序、删除。移出或删除卡组后，存档恢复为列表中的普通未归组卡片；删除卡组不删除存档。
- **手动排序**：未归组存档可在外层竖排列表中上下移动，包括移到卡组条目之前或之后；组内存档可在所属卡组内上下移动。卡组整体也可调整外层位置，带着组内顺序一起移动。
- 排序交互暂定为在管理操作中选择“调整位置”，用上/下移动当前项，确认保存、取消恢复进入排序前的位置；提供明确的移动提示，支持键盘和手柄，保持原卡片样式。排序期间普通上/下浏览与移动操作互斥，焦点跟随被移动项。
- 排序只在当前层级内生效；组内项移到组首/组尾后不跨组，外层未归组存档经过一个展开卡组时，以整组为相邻条目跳过，不插进它的子项。跨组移动或移出卡组使用明确的归组操作，避免排序意外改变归属。
- 继续游戏、新建、重命名、辅助模式、删除存档优先接入原有流程，保留扩展按钮与必要确认。
- 选择组内存档后，进入正常的地图选择/继续游戏流程，地图界面和关卡内不增加卡组界面或额外步骤。
- 首版支持选择多份存档组成卡组；拖放、多标签、自动规则、导入导出放到后续迭代；不把存档复制功能纳入首版。

首次导入时保留原存档的相对顺序，创建卡组时暂定放在首个被归组存档的位置；组内初始顺序沿用原列表顺序。之后以用户手动排序为准，展开/收起、返回菜单和重启游戏均保留该顺序。新发现的未归组存档默认追加到外层末尾，不重新排列已有项；移入卡组默认追加到组末，移出卡组暂定放在原卡组之后。UI 顺序独立于存档槽号，不重编号存档文件。具体管理按钮与动画节奏在原型查看后调整。

## 5. 技术方案

### 已确认的接入点

本机程序集包含 `Celeste.OuiFileSelect` 的 Enter、Leave、LoadThread，以及 `Celeste.OuiFileSelectSlot` 的 CreateButtons、OnContinueSelected、OnNewGameSelected、OnDeleteSelected 等方法。这里只确认其存在，不代表已验证其所有调用前置条件或第三方兼容性。

官方 Everest 补丁源码表明：

- 存档菜单已经支持扩展数量的存档槽，会扫描主存档和 Mod 附属文件推导槽号范围。
- 主存档缺失而 Mod 附属数据仍存在的槽位会被标记为异常，不能简单当成空槽覆盖。
- `Everest.Events.FileSelectSlot.OnCreateButtons` 允许其他 Mod 添加存档操作按钮。
- 原菜单存在按槽数组、逐槽移动和动画的处理；只缩小原立牌，不会自动解决大量存档时的构造、更新和加载成本。

推荐划分：

| 模块 | 职责 |
|---|---|
| CompactSaveDeckModule | 注册/卸载 Hook 和事件；设置启用状态；完整清理资源 |
| SaveCatalog | 发现有效槽位、保留缺失/损坏状态、提供只读摘要、增量刷新 |
| DeckRepository | 全局卡组、归属、外层与组内排序、展开与焦点状态的版本化持久化 |
| DeckView | 混合竖排列表、原卡片呈现、堆叠封面、展开/收起布局与焦点、有限动画 |
| SaveActionAdapter | 将选中槽位接入 Celeste/Everest 操作，处理返回路径和扩展菜单 |
| Diagnostics | 加载耗时、切换延迟、分配量、异常日志与兼容问题定位 |

优先使用公开事件与 On Hook。Load 时注册，Unload 时解除；不在每次切换卡组时创建 Hook。必要的私有访问/IL 修改集中封装，只在技术验证证明需要时引入。

**最先验证的架构问题**：能否保持未归组及展开后存档卡片的原有呈现和操作，同时对折叠组的子项避免不必要的构造、更新与绘制。如果做不到，需要调整适配方案；不能把所有原立牌仅设为不可见当作性能方案已经完成。其他 Mod 可能依赖具体 Oui 类型、选中状态或 Enter/Leave 路径，这些必须实际测试。

纵向导航使用“可见条目列表”：外层普通存档、折叠卡组封面、展开组标题及其子存档。条目 ID 与真实存档槽号分离，展开/收起只改变可见条目；实际继续/新建等操作仍使用原存档槽身份。按实际条目高度计算纵向位置，并维护稳定的滚动锚点，不能将列表位置直接当作存档槽号。

### 分类数据与存档安全

- 原版 `N.celeste` 和 Everest/其他 Mod 的附属文件仍由原有机制管理；卡组操作不移动、重编号或改写这些文件。
- 分类是跨存档的全局数据，不应仅存在某个存档的 `EverestModuleSaveData` 中，否则尚未选中存档时就难以正确读取全局卡组。
- 建议独立、带 schemaVersion 的元数据文件，路径通过游戏的存档路径 API 解析，不硬编码安装目录。
- 记录稳定的卡组 ID、名称、颜色、存档槽到卡组的映射、外层条目顺序、每组存档顺序，以及展开/焦点状态；摘要缓存应可随时重建。外层排序以“存档/卡组类型 + 稳定 ID”标识条目，不以可见行号或展开后的索引标识。
- 保存与恢复顺序时去重、清除已确认删除的引用、追加新发现的条目，保留其余用户排序。存档暂时不可读时保留对应位置和异常状态，不直接当作已删除。任何排序都不重命名主存档或附属文件，也不修改真实槽号。
- 元数据写入使用临时文件与替换机制，保留上一份有效内容；写入失败显示明确状态，不将失败当作已保存。
- 观察到槽位删除/重建时清理旧归属。对外部覆盖、备份恢复、槽号复用不能仅凭文件名断言是同一存档；检测到身份歧义时进入未分类或提示重新确认，不静默继承错误归属。具体判定方式在原型阶段验证。
- 卸载 Mod 后，已有游戏进度仍可从原存档菜单访问。分类元数据即使损坏，也应能将存档恢复显示为普通未归组卡片。
- 是否被 Steam Cloud 同步需单独验证，不默认承诺新元数据文件会自动同步。

### 性能设计

1. 初次进入建立槽位索引；优先取得首屏摘要，其他摘要逐步补齐。不能把加载时间简单转移成首次打开时的大卡顿。
2. 后台仅进行可安全隔离的文件 I/O 和纯数据解析；游戏状态、纹理、场景和输入更新留在主线程。不要为了生成摘要反复切换 `SaveData.Instance` 或加载所有 Mod 的活动存档。
3. 保存轻量摘要，缓存失效依据文件变化、游戏保存/创建/删除事件及必要的重新扫描；格式化字符串和排序结果也缓存。
4. 热态展开/收起及卡组跳转只更新内存中的可见条目和焦点，不读盘、不反序列化全部存档、不重建图集。
5. 仅更新/绘制可见卡片及少量缓冲项；折叠组子项不参与列表导航和逐帧动画。保持原卡片表现的同时验证按需构造/复用，避免按最大槽号创建与之等量的 UI 实体。
6. 展开/收起动画只作用于可见对象，可被连续输入打断；支持关闭/减少动画。保留未归组卡片的正常反馈，避免用全量重建布局或长时间锁定输入实现堆叠效果。

建议验收目标（尚未实测）：

- 在隔离数据集 **100 / 500 / 1000 个存档、10 / 50 / 100 个卡组** 下测试，覆盖稀疏槽号及大体积 Mod 存档。
- 缓存就绪后，展开/收起或跳组输入到对应变化首帧可见的 P95 延迟目标 ≤ 50 ms；动画时长与输入响应分开统计。
- 菜单稳定浏览时，本 Mod 主线程更新与绘制耗时 P95 目标 ≤ 2 ms；以维持 60 FPS 的整体帧预算为依据。
- 热态切换路径无同步存档读取；反复切换后内存不持续增长，空闲时避免重复分配和解析。
- 冷启动记录首个可操作界面、首屏摘要完成、全部索引完成三个时间；先取得基线再确定目标，不事先承诺任意大存档都瞬时加载。

## 6. 分阶段交付与验收

| 阶段 | 交付 | 通过条件 |
|---|---|---|
| P0 开发链路与接入验证 | 模板工程、net8.0 编译、引用路径、日志、最小菜单接入/退出 | 游戏成功加载；进入/退出无 Hook 泄漏；证明继续游戏与返回菜单路径可复用；确定避免全量立牌构造的办法 |
| P1 竖排堆叠原型 | 原样未归组卡片、示例卡组封面、原位展开/收起、组内竖排、已有存档继续操作 | 用户可查看堆叠样式并提出调整；原卡片表现保持；选择后进入正常游戏；展开/收起与返回位置稳定 |
| P2 卡组功能与排序 | 选择存档归组、卡组 CRUD、移入/移出、未归组/组内/卡组整体排序、搜索跳转、展开/焦点记忆、元数据持久化 | 重启后分类与手动顺序保留；排序取消可恢复；删除卡组恢复普通卡片；外部新增/删除不打乱其他项；UI 顺序不混淆槽号 |
| P3 完整存档操作 | 新建、命名、重命名、辅助模式、删除确认、扩展按钮适配 | 与原流程结果一致；完整处理 Mod 附属数据和取消操作；原菜单开关可恢复正常使用 |
| P4 性能与兼容 | 大规模数据测试、内存与帧耗时报告、中文/分辨率/输入验证 | 达到选定性能指标；明确支持的 Everest 版本及已知冲突 |
| P5 发布候选版 | 干净 zip、README、依赖版本、迁移说明和变更记录 | zip 根目录直接包含 everest.yaml；无游戏 DLL、私人存档或开发缓存；全新安装验证通过 |

规划中的测试应覆盖：删除后重建槽位、非连续编号、只有 Mod 附属数据的槽位、损坏文件、外部导入、分类文件损坏/写入失败、关闭 Mod、游戏内返回、连续快速展开/收起和窗口尺寸变化。另须对比未归组卡片与原菜单表现，测试多组同时展开、空组、移出最后一个存档、展开时下方条目移动与焦点保持，以及卡组 UI 不进入地图选择/关卡场景。

排序验收另覆盖：首尾边界、连续上/下移动、确认与取消、移动未归组项经过展开卡组、移动整个展开卡组、组内排序后收起再展开、重启后的顺序恢复，以及排序后进入游戏仍加载正确槽位。新建/导入/删除/重新归组后，应保留未受影响条目的相对顺序。

开发验证先使用隔离游戏/存档目录，并验证实际保存路径确已隔离；兼容性验证再使用用户存档的完整副本，包括关联的 modsave/modsession 文件。测试数据不直接生成到当前真实 Saves 目录。

## 7. 下一步的环境配置方案

当前不需要用户先安装 Unity、Lönn 或另一个 IDE。正式开发时依次完成：

1. 在工作区建立 `CompactSaveDeck` 项目和版本管理；使用官方 Core 模板作为基线。
2. 安装模板：`dotnet new install CelesteMod.Templates`。该命令尚未执行。
3. 将目标框架固定为 `net8.0`，配置 `CelestePrefix` 指向测试游戏目录。官方模板默认围绕 `Celeste/Mods` 内开发组织，外部工作区需要显式引用和受控部署步骤。
4. 审核并固定 NuGet 依赖版本，避免长期使用模板中的 `*` 浮动版本；引用游戏 DLL 时关闭 Copy Local。
5. 源码留在工作区，只向测试游戏的 `Mods/CompactSaveDeck` 部署 Mod 产物和自有资源。
6. 执行首次 restore/build，确认日志加载，然后用 VS 附加游戏进程调试。
7. 先采用关闭游戏后部署/重启的稳定循环。`CodeReload_WIP` 是可选加速手段，不能假定所有菜单 Hook、状态和资源都能安全热重载。
8. 完成 P0 后再锁定最低 Everest 版本和操作适配边界；P1 展示堆叠原型后根据用户反馈调整封面、间距与展开动画，保持竖排和原存档卡片要求。

本次调研没有执行上述安装、建项、构建或部署，因此这些是下一阶段的明确工作项。
